# testbot

This Android library acts like a season's `TeamCode` directory while remaining
independent of any real robot project. Use it to try framework APIs and catch
integration failures across the library, KSP processor, and consuming code.
Its package is `org.firstinspires.ftc.teamcode`, so the examples exercise the
same public extension boundary as a real consumer.

## Run

From the repository root, using the same JDK and Android SDK as the library:

```sh
./gradlew :testbot:testDebugUnitTest
./gradlew :testbot:assembleRelease
```

On Windows use `.\gradlew.bat`. Desktop unit tests need no emulator, connected
robot, or configured devices. Results appear in
`testbot/build/reports/tests/testDebugUnitTest/index.html`.

## Included setup

- `robot/Robot.kt`: single robot object, deferred component declarations, and
  property-based configuration. `initForTest` uses the normal initialization seam
  with an empty scope or fake hardware; pass `ComponentConfig.disableAll()` to
  disable every component.
- `component/Claw.kt`: scoped servo access and an enum FSM with public transition
  methods. Its logical state survives opmode transitions. The hold-open action
  explicitly closes on cancellation.
- `action/ClawActions.kt`: parameterized one-shot commands and a cancellable
  hold-open action that claims the claw as a requirement.
- `opmode/TestTeleOp.kt`: hold gamepad A to open, release to close. Inputs poll
  before one component-registry tick per loop, which also runs the scheduler.
  Both examples extend `RobotOpMode`, which owns session setup and cleanup.
- `opmode/TestAuton.kt` and `opmode/routines/SmokeAuton.kt`: annotated base and
  direct subclass using an alliance-aware sequence with actions and a path. The
  auton explicitly starts and samples recording; teleop omits recording.
- `src/test/`: fake FTC servo, component identity/state persistence, session
  lifecycle and scheduling checks, and
  assertions against classes generated by the real KSP processor.

KSP generates `Blue_SmokeAuton` and `Red_SmokeAuton` in
`org.firstinspires.ftc.teamcode.opmode.generated`, the annotated base's package
plus `.generated`. It generates nothing for the base or `IndirectSmokeAuton`.
Inspect outputs in `build/generated/ksp/debug/kotlin/` after a debug build.

## Hardware and deployment

The sandbox produces an AAR, not an installable Robot Controller APK. The sample
opmodes can be included in a separate FTC RC app for device testing. The sample
claw expects a servo named `testClaw` with positions 0.25 (closed) and 0.75 (open);
adjust those before using your mechanism.

Motion is disabled in `RobotConfig`, and the follower factory deliberately fails
if motion is enabled without configuration. Path tests verify construction,
alliance mirroring, and scheduler completion with disabled motion; they do not
simulate driving. To test a drivetrain, supply a tuned Pedro follower factory
and enable `Robot::motion` in the config.

Recording is opt-in. Desktop tests initialize the robot without calling
`startRecording()`, so they do not create match files. The sample auton opts in
from its opmode hooks using the library's default recording configuration. Keep real
season behavior in its own repository; keep general framework contract tests in
`:myrelib` and consumer integration examples here.
